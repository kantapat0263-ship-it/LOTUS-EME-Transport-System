# คิวต่อเนื่องและการยืมเฉพาะวัน

ใช้เมนูเดิม ไม่มีเมนูคิวประจำไซต์เพิ่ม

1. คนจัดรถเลือกใบขอในหน้าจัดกลุ่มเที่ยววิ่ง แล้วระบุวันสิ้นสุดคิว หรือขยายทริปที่ยังไม่เริ่มงานจากหน้าสรุปคิวรถประจำวัน ช่วงหนึ่งไม่เกิน 90 วัน
2. คนขอรถเห็นข้อความใต้วันที่ว่าคนขับและรถมีคิวอยู่ช่วงไหน กดดูรายละเอียดได้ และส่งคำขอให้คนจัดรถพิจารณาต่อได้ ข้อความนี้ไม่ยืนยันว่ารถว่าง
3. เมื่อตกลงยืม คนจัดรถเลือกงานปลายทางแล้วใช้ปุ่มปรับคิวเฉพาะวันนี้ เลือกยืมคนขับ รถ หรือทั้งคู่ ใส่เหตุผล และเลือกชดเชยหนึ่งวันเฉพาะเมื่อมีข้อตกลง
4. ระบบรักษาช่วงเดิมและรหัสทริปทุกวัน พักทริปต้นทางเฉพาะวันยืม แล้วสร้างคิวปลายทางที่เชื่อมกัน ทรัพยากรต้นทางที่ไม่ได้ยืมยังคงถูกจองไว้
5. หากยกเลิกก่อนเริ่มงาน ให้ใช้คืนคิวในแผงคิวต่อเนื่อง ระบบยกเลิกคิวปลายทางและคืนต้นทางพร้อมประวัติ การยกเลิกใบขออย่างเดียวไม่คืนคิวอัตโนมัติ
6. ยอดชดเชยแสดงเป็นค้างชดเชย นัดวันแล้ว หรือทำครบแล้ว เลือกวันว่างเพื่อสร้างคิวชดเชยแยก ช่วงเดิมไม่ถูกยืด และต้องกดยืนยันจบงานชดเชยเอง

ทริปที่เชื่อมคิวต่อเนื่องไม่ใช้ปุ่มแก้คนขับ รถ สถานะ ลบ หรือแทรก/โยกงานทั่วไป ต้องใช้คำสั่งในแผงคิวต่อเนื่องเพื่อรักษาการจองและประวัติ รุ่นนี้ยังไม่รองรับการแก้หมายเหตุรายจุด เปลี่ยนรูปแบบเส้นทาง หรือกำหนดเวลาตัด GPS ของทริปที่เชื่อมคิวต่อเนื่อง ปุ่มเหล่านี้ยังใช้กับทริปทั่วไปได้ตามเดิม

ใบคิวทั่วไปที่กดจบการใช้รถแล้ว (`gpsEndAt`) ไม่สามารถขยายเป็นคิวต่อเนื่องได้ เช่นเดียวกับการยืม คืน หรือยกเลิกนัดชดเชยหลังมีการจบการใช้รถ ระบบตรวจใบสดใน transaction ก่อนบันทึก

## ข้อมูลและการทดสอบ

`continuousBookings` เก็บช่วงเดิมและข้อยกเว้นรายวัน `trips` เก็บคิวจริงรายวัน `queueResourceDays` ทำให้การจัดคิวทั่วไปและคิวต่อเนื่องตรวจทรัพยากรร่วมกัน ส่วนเหตุผลและผู้อนุมัติอยู่ในบันทึกส่วนเจ้าหน้าที่ ผู้ขอเห็นเฉพาะข้อมูลการจองที่จำเป็น

ใช้ `npm run test:run`, `npm run typecheck`, `npm run test:queue` และ `npm run test:rules` ชุดฐานข้อมูลใช้ Firebase Emulator และ project ที่ขึ้นต้นด้วย `demo-` เท่านั้น การทดสอบในเบราว์เซอร์ใช้บัญชีและข้อมูลจำลอง ไม่ส่ง LINE และไม่เรียกแผนที่ภายนอก

การจัดใบขอเข้าทริปทั่วไปและคิวต่อเนื่องบันทึกการจัดปลายทางพร้อมทริปใน transaction เดียวกัน จึงไม่เกิดทริปสำเร็จแต่ใบขอยังไม่ถูกจัด หรือจัดปลายทางเดียวซ้ำในระหว่างบันทึก

การค้นหาคิวใช้ `startDate`, `compensationDates` และ `hasOpenCompensation` ซึ่งระบบคำนวณพร้อมการบันทึก ไม่ต้องสร้าง composite index และไม่ดึงประวัติทุกคิวมาค้นในเบราว์เซอร์

ผลตรวจหลังรวม main `b2a21a1` เมื่อ 6 ตุลาคม 2569:

- กฎสิทธิ์เดิม 27/27 กรณีผ่าน รวมทั้งหมด 569 กรณี
- ทดสอบกดผ่านเบราว์เซอร์ในเครื่อง: ขยายช่วง ยืมทั้งคนขับและรถ ใบงานเหลือหนึ่งเที่ยว นัด/ยกเลิกวันชดเชย และคืนไซต์เดิม ผู้ขอเห็นคิวในจอ 390 พิกเซลโดยไม่ล้นและแก้คิวไม่ได้

- ทดสอบแผนที่และส่ง LINE จริงอยู่นอกชุดทดสอบนี้

## การนำขึ้นระบบ

ผู้ใช้อนุมัติ DEPLOY เมื่อ 6 ตุลาคม 2569 ปล่อยฟีเจอร์ด้วย commit `e68709a` หลังรวม main ล่าสุดแล้ว ตรวจ `/api/version` บน production ตรงกับ commit; หน้า login/requests/daily-summary ตอบ 200 และ API คิวต่อเนื่องปฏิเสธการอ่านโดยไม่ล็อกอินด้วย 401

Firestore rules ที่ live คือ `3cbf074f-86ba-4bdf-abe0-c8968f1c050a` hash SHA256 หลังปรับ CRLF เป็น LF เท่ากับไฟล์ที่ตรวจ (`b0cc16afe0291d604d16f328f74b12098add55355babc89d8d2d9b2aa76b8512`)

หลังปล่อยพบว่า GitHub CI ติดตั้ง dependency ไม่ได้ เช่นเดียวกับ main ก่อนฟีเจอร์ เพราะ lock เดิมใช้ `@types/node` 20.17.17 ต่ำกว่า optional peer ของ Vite และ runner Node 20 ต่ำกว่า engine ของ Firebase Admin 14 แก้โดย pin เฉพาะ type เป็น 20.19.0 และเปลี่ยน CI เป็น Node 22 ไม่อัปเกรด package ของ runtime ผล `npm ci --dry-run` ผ่าน การยืนยัน CI จริงตรวจจากรอบใหม่หลัง push

ก่อนปล่อยต้องตรวจและเผยแพร่ `firestore.rules` ชุดเดียวกับแอป การบังคับ guard ทำให้แท็บแอปรุ่นเก่าจัดทริปด้วยวิธีเดิมไม่ได้ จึงต้องจัดช่วงเปลี่ยนรุ่นและโหลดหน้าใหม่ให้เรียบร้อย การปล่อยแอปเพียงอย่างเดียวไม่รับประกันการป้องกันการจัดชนกัน

ก่อนปล่อยได้ตรวจข้อมูลผู้ใช้จริงแบบอ่านอย่างเดียวแล้ว ผู้ใช้เดิมทั้ง 16 บัญชีมี `active: true` (เจ้าหน้าที่ 3 บัญชี) และสำรอง ruleset เดิม `86aa1529-9df7-461a-a1c6-404d47f56a9d` ไว้ การปล่อยนี้ไม่ย้าย/แก้ใบคิวเก่าและไม่สร้างข้อมูลทดสอบในฐานข้อมูลจริง
